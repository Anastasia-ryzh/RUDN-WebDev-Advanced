## Context

Проект использует React + TanStack Query для управления состоянием сервера, json-server в качестве mock API (`db.json`). Создание карточки реализовано через `useMutation` в `NewCardForm` с `mutationFn: createCard` и инвалидацией кеша `["cards"]` в `onSuccess`. Бэкенд (json-server) автоматически поддерживает `DELETE /cards/:id`.

Тип `Card` содержит поле `id`, но `BoardColumn` не передаёт `id` в `BoardCard` и не задаёт `key` в списке. `BoardCard` получает только `title` и `isDone`, интерактива нет.

## Goals / Non-Goals

**Goals:**
- Добавить API-функцию удаления в `client/src/api/cards.ts`
- Передать `id` карточки из `BoardColumn` в `BoardCard` и задать `key={card.id}` в списке
- Добавить кнопку удаления в `BoardCard` с подтверждением через `window.confirm`
- Удалить карточку из UI после успешного ответа сервера с инвалидацией кеша `["cards"]`
- Показать сообщение об ошибке, если удаление не удалось

**Non-Goals:**
- Анимация исчезновения карточки
- Drag-and-drop и сортировка
- Удаление нескольких карточек одновременно
- Кастомное модальное окно подтверждения

## Decisions

### Решение 1: Подтверждение удаления

**Выбрано:** `window.confirm` — стандартное диалоговое окно браузера.

**Альтернативы:**
- Кастомное модальное окно — требует создания нового компонента, дополнительных стилей и управления состоянием; избыточно для простого вопроса «да/нет»
- Удаление без подтверждения — противоречит спецификации: пользователь должен подтвердить действие

**Почему отклонено:** `window.confirm` покрывает требование спецификации без дополнительного кода и зависимостей.

### Решение 2: Момент удаления карточки из UI

**Выбрано:** Удаление карточки из UI только после успешного ответа сервера (`onSuccess`).

**Альтернативы:**
- Оптимистичное удаление — карточка сразу убирается из UI, а при ошибке сервера восстанавливается через `onError`; требует поддержания временного состояния удалённых карточек и логики отката

**Почему отклонено:** Карточек на доске немного, задержка незаметна. Оптимистичное удаление усложняет код ради ничтожного улучшения UX. При ошибке сервера карточка просто остаётся на месте — это корректное поведение.

### Решение 3: Обработка ошибок

**Выбрано:** `alert` с сообщением об ошибке при неудачном удалении.

**Альтернативы:**
- Toast-уведомения — требуют дополнительного компонента тоста, который в проекте отсутствует, и состояния для управления видимостью
- Inline-ошибка под карточкой — усложняет layout, требует позиционирования и состояния ошибки на карточку

**Почему отклонено:** `alert` — минимальный код без дополнительных зависимостей. В рамках этого тикета достаточно простого сообщения.

### Решение 4: API-функция deleteCard

**Выбрано:** `deleteCard(id)` отправляет `DELETE /api/cards/:id` и, как `createCard`, выбрасывает ошибку, если ответ не `ok`. Мутация живёт в `BoardCard`: при `onSuccess` вызывает `invalidateQueries` с ключом `["cards"]`, при `onError` показывает `alert`.

**Альтернативы:**
- Функция удаления в `BoardColumn` — нарушает принцип единственной ответственности, `BoardColumn` не должен знать про мутации
- Глобальный store (Zustand) для мутаций — избыточно, TanStack Query уже управляет серверным состоянием

**Почему отклонено:** `BoardCard` — единственное место, где нужна кнопка удаления. `invalidateQueries` в `onSuccess` обеспечивает обновление всего списка карточек.

### Решение 5: Передача id в BoardCard

**Выбрано:** `BoardColumn` передаёт `card.id` в `BoardCard` и задаёт `key={card.id}` при рендере списка.

**Альтернативы:**
- Генерация key на основе индекса — ненадёжно при будущем добавлении drag-and-drop и сортировки
- Хранение id только в DOM-атрибуте — требует `useRef` и парсинга, ненадёжно

**Почему отклонено:** `key` на основе индекса сломается при любой пересортировке. `card.id` из json-server — стабильный идентификатор, уже доступный в типе `Card`.

## Risks / Trade-offs

[Risk] Пользователь может случайно удалить карточку, нажав «ОК» в `window.confirm` → [Mitigation] `window.confirm` является подтверждением — пользователь должен явно нажать «ОК»

[Risk] Быстрое многократное нажатие на кнопку удаления → [Mitigation] `useMutation` не блокирует повторные вызовы; кнопка удаления отключается (`disabled`) через `isPending` мутации

[Risk] json-server может быть остановлен при тестировании → [Mitigation] Ошибка сети будет перехвачена, карточка останется на месте, пользователь увидит `alert`

## Migration Plan

Изменение не требует миграции данных — json-server поддерживает `DELETE /cards/:id` из коробки. Достаточно добавить клиентский код.

## Open Questions

Нет. Все технические решения определены на основе спецификации и существующего паттерна `NewCardForm`.
